# ADR-0013: 사이클 지표를 로컬 세션 기록에서 읽기 전용 명령으로 센다

상태: 채택 (사용자 결정, #4)

## 맥락

- [overview](../overview.md) 원칙 4는 측정되는 설정을 말하지만, 무엇을 어디서 세어 어디에 남길지 정하지 않았다.
- 파일럿(#2)의 공개 요약은 세션 기록을 손으로 세어 만들었다. 다시 세어 보니 메인 세션만 셌다. 그래서 다음이 어긋났다.
  - 서브에이전트 호출 5회가 빠졌다.
  - 호스트 내부 호출이 빠졌다.
  - 다른 Issue 브랜치에서 한 호출 14회가 들어갔다.
- 두 호스트의 기록 형식이 다르다.
  - Claude는 레코드마다 브랜치가 있다.
  - Codex는 세션 시작 브랜치만 있고, 서브에이전트 기록에는 브랜치가 없다.
  - 입력 토큰의 뜻도 다르다. Codex 값에는 캐시분이 들어 있다.
- 세션 기록에는 비공개 지침, 다른 프로젝트의 내용, 신뢰할 수 없는 텍스트가 들어 있다. 지표는 공개 Issue에 들어간다.

## 결정

- 지표, 범위, 둘 곳은 [metrics](../../specs/metrics.md)가 정한다. 단위는 Issue 사이클이고, 원칙 4의 "작업당"을 "사이클당"으로 맞춘다.
- `bin/devflow-metrics`가 두 호스트의 로컬 세션 기록을 읽어 정수만 출력한다.
  - 이 명령은 Issue를 쓰지 않는다.
  - 게시는 지금처럼 `devflow-state`가 한다.
- 범위는 Issue 브랜치에 있던 레코드다. 브랜치는 호스트마다 다른 곳에서 읽는다.
  - Claude: 레코드의 `gitBranch`
  - Codex: 작업 트리의 HEAD reflog
- 측정은 ship에서 통합하기 전에 Issue 브랜치에서 한다. 라우터의 review reference가 그 단계를 안내한다.

## 결과

- 사이클마다 같은 스크립트가 같은 규칙으로 센다. 공개 요약은 고정 형식의 한 줄이다.
- `bin/`이 하나 늘고 highRisk 경로에 신뢰할 수 없는 입력의 파서가 생긴다. 출력 스키마와 읽기 범위를 테스트로 고정한다.
- 다음은 세지 않는다.
  - 호스트가 기록에 남기지 않는 내부 호출
  - 다른 기기의 기록
  - eval 실행
  - 통합 뒤의 단계
  - worktree를 지운 뒤의 Codex 구간, 호스트가 지운 오래된 기록. 그래서 ship에서 잰다.
- 사람 개입과 필터 오탐은 장부에 손으로 센다. 정의는 spec에 둔다.

## 다시 볼 조건

- 호스트가 기록 형식을 바꿔 테스트 fixture와 실제 기록이 어긋날 때
- 호스트가 사용량을 구간별로 조회하는 공식 수단을 로컬에 제공할 때
- 여러 기기에서 한 Issue를 진행하는 일이 잦아질 때

## 검토한 대안

- **reference 절차와 매번 쓰는 스크립트**
  - 장점: 코드가 늘지 않는다.
  - 기각 이유: 파일럿 요약처럼 매번 다르게 셀 수 있다(사용자 결정).
- **`devflow-state`의 하위 명령**
  - 장점: 파일이 늘지 않는다.
  - 기각 이유: Issue를 게시하는 스크립트와 신뢰할 수 없는 기록의 파서가 한 프로세스에 모인다.
- **호스트 집계(Claude `cost-state`, Codex 누적 `total_token_usage`)를 주 원천으로 쓰기**
  - 기각 이유: Claude 집계는 종료한 세션에만 남는다. Codex 누적값은 브랜치 구간으로 나눌 수 없다. 둘 다 검산에만 쓴다.
- **세션 ID를 장부에 등록**
  - 장점: discover까지 잡는다.
  - 기각 이유: 등록을 빠뜨리면 값이 비고, 한 세션이 여러 Issue에 걸치면 겹친다(사용자 결정).
- **호스트 텔레메트리(OpenTelemetry 등)**
  - 기각 이유: 외부 전송이다.
