# ADR-0003: Issue를 상태의 진실 원천으로

상태: 채택 (사용자 관행 + 합의한 문서 체계). 개정: 작업 장부, Issue 입출력 필터, 무인 구간 게시 보류를 더했다.

## 맥락

- 기존 프로젝트들은 compact 뒤에도 작업을 잊지 않으려고 Issue로 추적해 왔다.
- 그런데 상태를 Issue 본문에 날짜별 섹션으로 계속 덧붙이고, 댓글이 수십 개씩 쌓인다.
- Issue와 같은 내용을 담은 긴 프롬프트와 handoff 파일도 따로 만든다.
- compact 뒤 호스트는 최근 파일 몇 개만 다시 읽고, 5,000토큰이 넘는 파일은 경로만 남긴다.
- 공개 저장소의 Issue와 PR 텍스트는 프롬프트 주입 경로다. 2026년 공개된 사례에서 코딩 에이전트 세 종이 숨은 HTML
  주석과 Issue 본문의 지시를 따라 비밀값을 공개 댓글로 게시했다.
- 작업 번호, 시도 횟수, 대기 중인 결정처럼 작업마다 바뀌는 값은 Issue에 두면 공개 편집이 작업마다 생긴다.
- 소유자의 전역 지침은 외부에 공유되는 효과를 대화형 턴에서만 허용한다.

## 결정

- Issue 본문은 intent와 **덮어쓰는** 현재 상태 블록을 담는다.
- 댓글은 **추가만 하는** 체크포인트를 담는다.
- Issue는 단계 경계, 결정, 막힘에서만 쓴다. 작업 단위의 진행은 로컬 작업 장부(`.work/devflow/i<n>/ledger.json`)에
  둔다. (사용자 결정)
- Issue는 스크립트 하나로만 읽고 쓴다. 읽을 때 작성자와 형식을 거르고, 쓸 때 출력 필터를 거친다. 이 스크립트를
  거치지 않는 Issue 쓰기는 훅이 막는다.
- 재개 카드는 `.devflow.json`이 있는 저장소에서만 출력한다.
- 무인 구간에서는 게시하지 않고 장부에 쌓았다가 다음 대화형 턴에 게시한다. (사용자 결정)
- 대화형 턴에서 묻지 않고 하는 Issue 쓰기: 상태 블록, 체크포인트, ship에서의 종료, 범위가 끝나지 않은 같은 Issue의
  재오픈, 사용자가 미루기로 정한 것과
  재현된 결함의 후속 Issue 생성. 그 밖의 후속 후보는 ship 때 목록으로 제안한다. (사용자 결정)
- 대화형 작업에서는 작업 단위가 끝나면 `/clear` 후 재개 카드로 다시 시작한다. 무인 실행은 작업마다 서브에이전트로
  새 컨텍스트를 쓴다.
- 공개할 수 없는 근거만 로컬 비공개 파일에 둔다.
- 형식, 예산, 필터는 [documents](../../specs/documents.md)가 정한다.

## 결과

- 이어서 작업할 때 읽는 양이 일정하다: Issue 본문, 최신 체크포인트 하나, 장부.
- 다른 기기에서는 장부가 없어 Issue의 현재 상태까지만 이어진다.
- 공개 저장소의 Issue에는 공개 가능한 요약만 쓴다.
- Issue 쓰기는 원격 쓰기다. 프로젝트별로 AGENTS.md에 상시 허용 문장이 있어야 묻지 않고 갱신한다.
- 소유자의 전역 지침은 소유 저장소의 Issue 생성과 갱신을 대화형 턴에서 상시 허가한다. devflow는 그 가운데 위의
  쓰기만 쓴다. Issue 본문의 이전 버전은 공개 기록으로 남으므로 공개 가능한 내용만 쓴다.

## 검토한 대안

- 커밋되는 intent.md → spec.md → plan.md 체인(AI-native SDLC 플레이북): 계약 변경에는 `docs/specs/`로 채택했다.
  계획은 기존 프로젝트들이 비공개로 두어 왔으므로 기본은 로컬에 두고 PR에 요약만 남긴다.
- 로컬 진행 파일만 쓰기: 다른 기기나 다른 호스트에서 보이지 않는다.
- 작업 위치까지 Issue 상태 블록에 쓰기: 기기를 바꿔도 세부가 이어지지만, 공개 편집이 작업마다 생기고 주입 표면이
  넓어진다.
