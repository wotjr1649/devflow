# ADR-0029: 반복 보고 결함은 arm을 분리한 결과 eval로 재고, trigger 실행기는 그대로 둔다

상태: 채택 (#99, 2026-10-29 사용자 결정: 결과 eval 신설 승인, #73의 "평가기 수정" 제외는 이 장치를 막지 않음, 셀당 14회). 개정: 결과 eval은 요청할 때만 쓰는 도구이고 수용 기준이나 출시 조건이 되지 않는다([ADR-0030](ADR-0030-enforce-at-impact-boundaries.md), #104).

## 맥락

eval 계약은 결과 eval을 두지 않았다. 스킬 본문은 리뷰와 사이클 지표로 보고, 같은 실수가 반복되면 장치를 만드는 Issue를 열기로
했다. #80의 재발 측정은 현재 main 945dbd8에서 셀당 14회, 두 판정자로 했다. 그 결과 pr-review-workflow의 세 보고 결함이 다시 나왔다.
- 미제공 상태 단정: Claude 07A 9/14, 02B 4/14.
- Codex 03B 입력 개수 오기: 2/14.
- 공급 상태를 통합 관문으로 바꾸는 결함: 1/14.

뒤의 두 결함은 N151·N160에서도 관측됐다. #80까지의 관측은 일회용 작업 스크립트와 수동 판정이어서, 후보를 같은 방식으로 다시 재거나
비교할 수 없었다.

## 결정

- `bin/devflow-behavior-eval`을 따로 둔다. trigger 실행기는 바이트 그대로 두고 export만 재사용한다.
  - trigger 실행기는 자기 파일 해시로 예산 이어 실행의 동일성을 검사하므로, 고치면 기존 부분 결과를 이어 실행할 수 없다.
- arm은 고정 revision의 추적 파일 묶음이다. 사례·grader·실행기는 실행기를 부른 커밋 하나에서 가져와 두 arm이 같은 것을 쓴다.
  - 작업 트리를 복사하면 ignore된 비공개 파일이 actor에게 가고, 기준선 커밋에는 새 사례가 없기 때문이다.
- Claude는 사례와 arm만 담은 shim plugin으로 `claude plugin eval`을 슬롯마다 1회 부른다.
  - 대상 plugin을 그대로 쓰면 그 skill이 native 목록에 실려 arm이 섞인다.
  - 슬롯마다 부르는 것은 ABBA 순서를 지키기 위해서다.
- Codex는 같은 실행 폴더를 node로 만들고, trigger와 같은 `codex exec` 인자와 3회 judge를 쓴다. 저장소 안 시험 프로필의 설치본은
  명령행 override로 꺼지지 않는다(2026-10-29 확인). 그래서 귀속은 "실행 폴더 skill 전문 읽기, 실행 폴더 밖 읽기 없음"으로 확인한다.
- 모든 명제를 llm grader로 판정한다.
  - 전체 응답에 regex를 적용하면 인용·부정 문장을 오기로 세고 다른 수를 놓친다(검수 재현).
  - 과업 수행 grader를 따로 두어, 일하지 않은 답이 결함 없는 답으로 세이지 않게 한다.
- 채택은 사전 고정 규칙으로 정한다: 완결, 판정 가능, 수정 셀 합 감소, 회귀 셀은 후보에 불리하게 계산해도 비악화, 반대 조건 유지.
  결과는 셀별 관측 수와 규칙 충족 여부로만 보고한다.

## 대안

- trigger 실행기에 behavior 모드 추가: 실행기 해시가 바뀌어 trigger 이어 실행이 깨지고 두 계약이 한 파일에 섞인다.
- 사례마다 `--runs 14`로 한 번에 실행: 비용은 같다. arm별로 몰아 돌리면 시간·호스트 상태가 arm과 묶이므로 택하지 않았다.
- Codex 시험 프로필에서 devflow를 끄거나 arm마다 다시 설치: 프로필 설정을 바꿔야 한다. 읽기 귀속 확인으로 대신했다.
- regex 판정: 결정론이지만 의미를 구별하지 못한다. 보조 표지로만 쓴다.

## 결과

- 결과 eval은 수동이고 유료다. 실행 전에 사용자가 pilot과 총예산을 정한다.
- 한 슬롯의 진행 중 초과는 남은 예산 여유분 규칙으로만 줄인다.
- judge가 host마다 달라 host 사이 비교는 하지 않는다.
- B·K 사례는 #80에서 이미 쓴 소비 자료다. 일반화 근거는 새 holdout 한 사례의 관측뿐이다.
